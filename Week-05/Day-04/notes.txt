1. Introduction & Task Automation Concepts
--------------------------------------------------------------------------------------------------------------------------------------
* Objectives of Job Scheduling:
    -> Admin / Defensive  : Automate periodic system backups, rotate log files, maintain system performance without manual effort.
    -> Hacker / Offensive : Automate target scanning scripts (e.g., `MySQLscanner.sh`) during off-hours, school, or work hours.

* System Startup Automation:
    -> Purpose : Automatically launch required background services (e.g., `PostgreSQL` for Metasploit) upon system boot.
    -> Benefit : Eliminates the need to manually start database daemons or network listeners before initiating attacks/tasks.

📌 Summary
    -> Job scheduling executes routine tasks unattended during idle hours.
    -> Startup automation ensures essential pentesting services are ready immediately after boot.

✅ Exam Key Points
    -> Core daemon responsible for background job scheduling: `crond`.
    -> Key configuration file location for system-wide scheduled jobs: `/etc/crontab`.


2. Cron Architecture and Time Syntax Breakdown
--------------------------------------------------------------------------------------------------------------------------------------
* Components:
    -> `crond`   : Background daemon checking for scheduled jobs at precise intervals.
    -> `crontab` : System configuration table storing time syntax, user context, and absolute execution paths.

* System-Wide `crontab` Field Structure:
    `M  H  DOM  MON  DOW  USER  COMMAND`

* Time Fields Breakdown (Fields 1 to 5):
  Field | Time Unit        | Range / Accepted Values
  ------+------------------+-----------------------------------------------------------
   1    | Minute           | 0–59
  ------+------------------+-----------------------------------------------------------
   2    | Hour (24-hr)     | 0–23 (e.g., 13 = 1 PM)
  ------+------------------+-----------------------------------------------------------
   3    | Day of Month     | 1–31
  ------+------------------+-----------------------------------------------------------
   4    | Month            | 1–12 (Must use numerical value, e.g., 3 = March)
  ------+------------------+-----------------------------------------------------------
   5    | Day of Week      | 0–7 (Both 0 and 7 represent Sunday)
  ------+------------------+-----------------------------------------------------------

* Field Syntax Rules:
    -> Wildcard (`*`)     : Represents "every" or "all" units of time (e.g., every month).
    -> Range (`-`)        : Defines contiguous time frames (e.g., `1-5` = Monday through Friday).
    -> List / Comma (`,`) : Defines non-contiguous values (e.g., `15,30` = 15th and 30th days; `2,4` = Tuesday and Thursday).

📌 Summary
    -> System crontab uses 7 total fields (5 for time, 1 for user context, 1 for command path).
    -> `*` = every, `-` = range, `,` = multiple discrete values.

✅ Exam Key Points
    -> Numerical representation of Sunday: `0` or `7`.
    -> Value required for Month field: Pure numbers only (`1–12`), textual names like "March" are invalid.

3. Editing `crontab` & Practical Examples
--------------------------------------------------------------------------------------------------------------------------------------
* Editing Methods:
    -> CLI Command : `crontab -e` (Opens default terminal editor; e.g., `/bin/nano`).
    -> Text Editor : Direct edit via elevated GUI/text editor (e.g., `leafpad /etc/crontab`).

* Real-World Execution Examples:
  Scenario                                 | Crontab Syntax
  -----------------------------------------+-------------------------------------------------------------------
  Daily scan at 2:30 AM (Mon–Fri)          | `30 2 * * 1-5 root /root/myscanningscript`
  -----------------------------------------+-------------------------------------------------------------------
  Weekly backup (Every Sunday at 2:00 AM)  | `00 2 * * 0 backup /bin/systembackup.sh`
  -----------------------------------------+-------------------------------------------------------------------
  Bi-monthly backup (15th & 30th at 2 AM)  | `00 2 15,30 * * backup /root/systembackup.sh`
  -----------------------------------------+-------------------------------------------------------------------
  Nightly scan at 9:00 AM (Every day)      | `00 9 * * * user /usr/share/MySQLsscanner.sh`
  -----------------------------------------+-------------------------------------------------------------------
  Summer weekend scan (June–Aug at 2 AM)   | `00 2 * 6-8 0,6 user /usr/share/MySQLsscanner.sh`
  -----------------------------------------+-------------------------------------------------------------------

* Preset Time Shortcuts:
    -> `@yearly`
    -> `@annually`
    -> `@monthly`
    -> `@weekly`
    -> `@daily`
    -> `@midnight`
    -> `@noon`
    -> `@reboot`

    -> Usage Example : `@midnight user /usr/share/MySQLsscanner.sh`

📌 Summary
    -> Always use full absolute paths for scripts in the command field (e.g., `/usr/share/script.sh`).
    -> Time shortcuts replace the first 5 numerical fields for standardized routines.

✅ Exam Key Points
    -> Command to safely edit user crontab: `crontab -e`.
    -> Shortcut directive used to run a task once immediately upon boot: `@reboot`.

4. Automating Startup Services (`rc` Scripts & Runlevels)
--------------------------------------------------------------------------------------------------------------------------------------
* Boot Process Architecture:
1. Kernel initializes hardware and loads kernel modules.
2. Kernel starts primary initialization daemon (`init` / `initd`).
3. Daemon executes runlevel scripts located under `/etc/init.d/rc`.

* Linux Runlevels Table:
  Level | State / Mode
  ------+-----------------------------------------------------------
  0     | Halt system (Power off)
  ------+-----------------------------------------------------------
  1     | Single-user mode (Minimal diagnostic state, no network)
  ------+-----------------------------------------------------------
  2–5   | Multiuser modes (Standard operational environments)
  ------+-----------------------------------------------------------
  6     | Reboot system
  ------+-----------------------------------------------------------

📌 Summary
    -> Boot scripts located in `/etc/init.d/rc` manage initialization tasks.
    -> Runlevels dictate which services start depending on operational states.

✅ Exam Key Points
    -> Runlevel number for minimal single-user maintenance: `1`.
    -> System state associated with Runlevel `6`: System Reboot.


5. Managing Boot Services via CLI (`update-rc.d`) and GUI (`rcconf`)
--------------------------------------------------------------------------------------------------------------------------------------
* Verification of Running Processes (`ps` + `grep`):
    -> Check service status : `ps aux | grep postgresql`
    -> Output indicating process isn't running: Returns only the `grep` search process itself.

* CLI Management using `update-rc.d`:
    -> Enable service at boot : `sudo update-rc.d postgresql defaults`
    -> Verification after reboot: `ps aux | grep postgresql` shows active binary path (e.g., `/usr/lib/postgresql/...`).

* GUI Management using `rcconf`:
    -> Installation : `sudo apt-get install rcconf`
    -> Execution    : `sudo rcconf`
    -> Interaction  : Scroll list, press `Spacebar` to check/uncheck service, `Tab` to navigate to `<OK>`, press `Enter`.

📌 Summary
    -> CLI Service Persistence : `update-rc.d <service_name> defaults`
    -> GUI Service Persistence : `rcconf` TUI interface.

# ✅ Exam Key Points
    -> Command syntax to enable PostgreSQL at boot via CLI: `update-rc.d postgresql defaults`.
    -> Terminal command used to filter active processes: `ps aux | grep <process_name>`.
